How it works

The proxy runs inside the Paseo daemon, as part of the plugin. There is no external service.

The injected tools

When an agent session opens, the plugin adds its github_* tools to it (Paseo exposes plugin agent tools to the agent as MCP tools). Every agent gets them; sessions opened for history do not. With the soft rule on, a short instruction is also added to the system prompt: saved when an agent is created (the only path on Paseo 0.16, marked in the agent metadata) and appended when a session opens on Paseo 0.17 or later, and each tool description says to use it instead of gh or curl.

The pipeline of one call

  1. Classify. A curated tool states its action (for example create_pr). github_api is classified from the request: the method, the path, or the GraphQL root fields.
  2. Owner allowlist. Every owner the call touches must be allowed. A call that cannot be tied to an owner is refused, unless every owner is allowed.
  3. Policy. Each needed action is checked. A matching deny rule wins, then an allow rule, then the default permissions. A denial returns a message naming the rule and reason.
  4. Cache. A read younger than the TTL is answered locally. An older one is sent with If-None-Match; a 304 costs no rate limit and restarts the clock.
  5. Credentials. The active source is used, then the other if fallback is on. With GitHub Apps, the App is chosen by the owner of the call: the App claiming it, else the default App. A credential that is rate limited is skipped until it resets.
  6. Response. The rate-limit headers are recorded, the response is cached, a write drops the cached reads of that repository, and the call is added to the activity log.

Cache

Entries are keyed by method, URL and request body, kept in memory and in cache.json so they survive a restart, and trimmed oldest-used first (500 entries or about 25 MB). Reads are served locally for the TTL (30 seconds by default, 0 to 3600, set in the Policy tab). Past it, the saved ETag is sent. GraphQL queries have no ETag, so they are cached by TTL only; mutations are never cached.

Webhooks and wake-ups (optional)

Off by default. When enabled in the Auth tab, the plugin starts a small HTTP listener (default 0.0.0.0:8787, every interface; set 127.0.0.1 to keep it on this machine; only POST /webhook and GET /healthz, bodies up to 1 MiB). GitHub needs a public URL, so you put a tunnel or reverse proxy (for example cloudflared) in front of it; the plugin does not create one. Each delivery must carry a valid X-Hub-Signature-256 (HMAC-SHA256, constant-time compare) made with the webhook secret of one of your GitHub Apps, and its owner must be one that App serves. Secrets are stored only in secrets.json. Repeated delivery ids are dropped. The Overview tab counts each delivery as delivered to a subscriber (it woke an agent), ignored (no subscriber, a ping or an unused event type) or rejected (bad signature, wrong owner, repeated), per minute for the last 30 minutes.

An accepted event drops the cached reads it makes stale, so the next read is fresh without waiting for the TTL; ETag revalidation stays the fallback. It also wakes the agents whose github_subscribe subscriptions match (checks completed on a pull request, a commit, a branch or a tag; review; comment, optionally mentioning a handle; PR opened, merged, closed or auto-merge changed; merge queue started or ended; push; release published): a short prompt with the event, repository, pull request, branch or tag, plus a hint to read the details with the github_* tools. Subscriptions are one-shot by default, expire after 6 hours by default (ttl_hours up to 7 days), and wake-ups are rate limited per agent. In the GitHub App's settings, subscribe it to the events check_run, check_suite, issue_comment, merge_group, pull_request, pull_request_review, pull_request_review_comment, push, release, status and workflow_run.

Client API for gh and git (optional)

Off by default. When enabled in the Auth tab, the plugin starts a second HTTP listener, separate from the webhook one (default 127.0.0.1:8788). It serves only /v1/* and GET /healthz, so it is never reachable through the webhook tunnel. GET|POST|PATCH|PUT|DELETE /v1/rest/{path} and POST /v1/graphql (with X-Proxy-Repo) go through the same owner allowlist, policy, per-owner GitHub App, rate limits, cache and activity log as the tools, so a gh shim that talks to a github-proxy works with GH_PROXY_URL pointing at it. A denial is 403 JSON naming the rule and the action. An optional bearer token is stored in secrets.json; with no token only this machine can call and a non-loopback bind is refused.

POST /v1/git-credential and the helper script git-credential-helper.mjs (embedded in the plugin and written to its data directory) let git fetch and git push over HTTPS work: only https://github.com/owner/repo is answered, with an installation token of the App serving the owner, limited to that repository. Git cannot tell a fetch from a push, so the token is read-only unless the policy allows Write file and Create branch there. New agent sessions can get GH_PROXY_URL, GH_PROXY_TOKEN and, when a GitHub App is configured, the git configuration automatically (a separate switch; the helper is added after the machine's own git helpers, which win where they have a credential, and it answers nothing rather than blocking git when it cannot issue a token); it affects only sessions opened afterwards, and is independent of the forbid gh/curl rules, which are about raw access.

Rate limits

The plugin tracks x-ratelimit-* per credential (the gh CLI and each GitHub App) and per resource (core, graphql, search). A credential is blocked until its reset (the other Apps keep working) when a response says the limit is exhausted, carries retry-after, or reports a secondary limit. With nothing left to try, the agent gets a cached answer marked as stale when one exists, and otherwise an error such as Retry at 14:07 (in about 12 min). The Overview tab shows the remaining count, a live countdown, and a warning when a limit is nearly used up.

Policy

A policy is a default list of allowed actions (from a preset, Full on a fresh install) plus ordered rules. See the reference for the actions and how generic calls are classified. The generic github_api tool can never bypass a rule: a merge through it needs both merge and generic_api_write.

What is stored, and where

FileContents
config.jsonActive source, fallback, allowed owners, TTL, soft rule, hard rule, policy.
apps.jsonThe GitHub Apps: organization, App ID, installation ID, extra owners, default flag. No secret.
secrets.json (0600)The private key and the webhook secret of each GitHub App, and the client API token.
subscriptions.jsonThe agents' event subscriptions. No secret.
cache.jsonCached GitHub responses, kept per credential so an answer is never shared between Apps.

All files are in $PASEO_HOME/plugin-data/lerenn/paseo-github-proxy/. The activity log and counters live in memory and reset when the plugin restarts.

Limits

  • The soft rule is an instruction. An agent with a shell can still run gh.
  • The hard rule (Block gh/curl commands) only sees permission requests, so an agent in a bypass mode is never checked. It matches command words, it is not a sandbox: a script file or a command built at run time gets through. Block egress to GitHub on the daemon machine for a real block.
  • GraphQL scoping is best effort: it checks the repository you pass and owner: values in the query. Queries by node ID cannot be scoped to an owner and are refused unless every owner is allowed.
  • On Paseo 0.16 the soft rule only reaches agents created after it was turned on.
