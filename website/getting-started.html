Getting started

Install the plugin, connect GitHub, allow an owner. Agents can read right away; you enable writes when you want them.

  • Paseo 0.17 or later (the plugin declares >=0.17.0).
  • Plugins enabled on the daemon: Settings → Plugins → Enable plugins, or pluginsEnabled: true in the daemon's config.json.
  • For the gh source: the GitHub CLI installed and logged in on the daemon machine. For the App source: a GitHub App installed on your account or organization.
Plugins are trusted, unsandboxed code. The server part runs on the daemon machine, runs gh when you choose that source, and stores the App private key there.

1. Install the plugin

paseo plugin install github:lerenn/paseo-github-proxy

Check that paseo plugin ls shows paseo-github-proxy as running, then open GitHub Proxy in the sidebar (or Command Center → "Open GitHub Proxy"). Sessions already open pick up the tools when they next reopen.

2. Choose a credential source

Open the Auth tab and pick one active source.

Local gh CLI

gh auth login

Run it on the machine where the Paseo daemon runs, then press Check gh. The plugin reads the token with gh auth token and keeps it for five minutes. It stores nothing.

GitHub App

Create a GitHub App with the permissions you need (for the PR workflow: Contents, Pull requests, Issues and Checks, plus Metadata read; write only where you want writes) and install it. Then enter:

FieldWhere to find it
App IDThe App's settings page.
Installation IDThe number at the end of the installation URL, /settings/installations/<id>.
Private keyGenerate one on the App's settings page and paste the PEM.
The key is write-only. It is saved to secrets.json (mode 0600) in the plugin's data directory on the daemon machine, never written to the config, never logged, and never sent back to the app: the page only shows a fingerprint. Paseo has no secret vault for plugins, so keep the daemon's home private.

Press Test connection. Optionally turn on Fall back to the other source on rate limit: when the active source is exhausted, calls use the other one until its limit resets.

3. Allow owners

In Auth → Allowed owners, open the dropdown and check the GitHub users and organizations agents may act on. The list comes from the active source; type a name to add one that is not listed. The default * allows every owner; replace it to restrict agents. If you clear the list, every call is refused.

4. Set the policy

The Policy tab starts on Read-only. Pick a preset, adjust the default permissions in one checklist dropdown, and add rules. A rule picks its repositories (listed from the allowed owners, or typed as a pattern such as acme/*) and its actions from checkable dropdowns:

Preset: PR workflow
Rule 1  deny   acme/prod     merge, delete_branch, force_push   "humans merge prod"
Rule 2  allow  lerenn/*      merge

Use Test this call to see what the policy says about a REST path or GraphQL query without sending anything.

5. Try it

Ask any agent to list the open pull requests of a repository. In the Activity tab you will see the call as Allowed; ask again within 30 seconds and it shows as Cached. Ask it to merge one under Read-only and it shows as Denied with the reason the agent received.

Optional: steer agents away from gh and curl

In Policy → Behaviour, turn on Forbid direct use of gh, curl and raw GitHub. An instruction is added to every agent's system prompt and to each tool description telling it to use the github_* tools. It is a soft rule, not a sandbox, and applies to sessions opened after you change it.
